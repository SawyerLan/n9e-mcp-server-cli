# 模块 06：写命令与安全控制

## 1. 模块目标

本模块用于实现 CLI 首批写命令，并补齐最基本的安全控制。

当前建议范围仅包括：

- `mutes create`
- `mutes update`

## 2. 为什么写命令后置

原因：

- 写命令风险更高
- 需要确认参数完整性
- 需要处理 `--read-only`
- 需要处理交互确认或跳过确认

因此应在只读命令跑稳后再做。

## 3. 推荐行为

### `--read-only`

要求：

- 在 CLI 模式下，写命令必须显式检查
- 如果开启 `--read-only`，应直接报错并退出

### `--yes`

要求：

- 用于跳过确认
- 只对写命令生效

建议行为：

- 若没有 `--yes`，可在交互终端下提示确认
- 若是非交互环境，建议要求必须传 `--yes`

### 输出结果

建议成功后输出：

- 资源 ID
- 简短成功消息

不要只输出“ok”。

## 4. 参数来源建议

写命令参数较多，不建议第一版只靠大量 flag 堆砌复杂对象。

建议分阶段：

1. v1 先支持核心 flag
2. 如果后续复杂度过高，再补 `--file` 或 `--json`

当前 `mutes` 相关字段较多，后续很可能需要结构化输入扩展能力。

## 5. 业务调用建议

CLI 写命令仍应只调用 `pkg/app`：

- 校验逻辑由 `pkg/app` 承担
- CLI 层只负责参数收集、确认、输出

## 6. 风险点

### 风险 1：误操作

规避：

- 默认确认
- 支持 `--yes`
- 成功输出明确资源信息

### 风险 2：`read-only` 被绕过

规避：

- 在写命令入口统一守卫

### 风险 3：参数 flag 爆炸

规避：

- 第一版只支持必要字段
- 复杂字段后续再增强输入方式

## 7. 本模块建议产出

- 写命令入口
- 写命令守卫
- 交互确认逻辑
- 成功与失败输出规范

## 8. 验收标准

- `--read-only` 下写命令不可执行
- `--yes` 能跳过确认
- 成功时输出创建或更新结果
- 失败时保留足够的 API 错误上下文
