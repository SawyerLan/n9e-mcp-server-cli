- 帮助开发者快速理解 CLI 模式的整体目标、模块边界和推荐顺序

## 2. 推荐开发顺序

建议严格按下面顺序推进：

1. 模块 01：统一目标、范围和阶段边界
2. 模块 02：先收敛配置与认证入口
3. 模块 03：抽出 `pkg/app` 共享业务层
4. 模块 04：搭 CLI 命令骨架
5. 模块 05：实现首批只读命令
6. 模块 06：再接写命令
7. 模块 07：统一输出、错误处理和测试补齐

原因：

- 模块 02 和模块 03 是 CLI 可复用基础
- 模块 04 是命令入口框架
- 模块 05 适合先验证架构可行性
- 模块 06 风险更高，应该后置
- 模块 07 应贯穿开发，但最好在前面模块成型后统一收口

## 4. 模块职责概览

- 分阶段实施顺序
- 模块之间的依赖关系

- 一份足够明确的实施地图

## 5. 推荐分工方式

如果多人并行，建议按下面分法：

1. 一人负责模块 02 和模块 04
2. 一人负责模块 03
3. 一人负责模块 05
4. 写命令模块 06 在前面稳定后再接
5. 模块 07 由主开发者统一收口

如果单人推进，建议一次只推进一个主模块，不要同时大范围改 `pkg/api`、`cmd`、`internal/cli`。

## 6. 建议里程碑

### 里程碑 A：基础可跑

完成标准：

- CLI 骨架可启动
- 环境变量认证可复用
- 至少一个只读命令可执行

### 里程碑 B：首批可用

完成标准：

- 首批只读命令全部可用
- 支持 `json` 输出
- 错误处理与退出码已统一

### 里程碑 C：具备写能力

完成标准：

- `mutes create/update` 可用
- `--read-only` 和 `--yes` 生效

### 里程碑 D：可交付

完成标准：

- 测试补齐
- README 更新
- CLI 模式可对外说明和试用

## 7. 一句话建议

后续开发请优先按模块推进，不建议直接“想到一个命令就加一个命令”。先把配置、共享层和 CLI 骨架打稳，后面的命令实现会顺很多。
